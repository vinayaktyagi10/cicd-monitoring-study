--- E3 (CPU stress detection) — SEVERE DEGRADATION ---
Original 20 runs: 20/20 detected, mean 5.65s.
This run: runs 1-3 detected normally (3.02s, 3.52s, 4.53s — consistent with
the original distribution). From run 4 onward, peak_cpu_percent read exactly
35.24871610144722 for four consecutive runs (4-7), then exactly 0.0 for
every remaining run (8-20) — a flat, unmoving signal, never crossing the 60%
detection threshold, for 17 straight runs.
  mean=3.69s stdev=0.63s min=3.02s max=4.53s  (n=3/20 detected)

Hypotheses for the E3 collapse (not confirmed — listed in order of
plausibility, worth investigating before trusting this run's numbers):

1. The app container is reused across all 20 runs in this script (unlike
   E1/E2/E4, which restart per run or per case) — see exp3_cpu_stress.py,
   main(): bring_up() is called once, not per run. If the app process itself
   got into a bad state after several back-to-back 8-thread CPU bursts (e.g.
   a stuck thread, an unhandled exception in the self-monitoring loop in
   app/main.py), later /cpu requests could silently fail — stress_worker()
   swallows all exceptions (`except Exception: pass`), so a failing request
   would not be visible in this script's own output.
2. The identical repeated value (35.24871610144722, four times exactly) is
   consistent with Prometheus returning a stale last-known sample rather
   than a fresh one — this happens when a scrape target stops updating.
   Prometheus holds a metric's last value for a staleness window
   (default 5 minutes) before marking it stale; the later flip to a clean
   0.0 is consistent with that window expiring and Prometheus reporting a
   genuine (idle) reading once no more data arrived at all.
3. This run had less free memory (1.6GiB free vs. more headroom originally)
   and a non-trivial load average — host contention could have caused
   request timeouts or scheduling delays severe enough to prevent the stress
   threads' requests from ever landing.

None of these is confirmed; distinguishing between them requires re-running
E3 in isolation (not immediately after E1/E2/E4 in the same session) with
`docker logs` on the app container captured throughout, which was not done
here.

--- Known gap found while writing this up ---
None of the raw CSV schemas include a timestamp or run-date column, so a
reproduction run appended to the same file is only distinguishable from the
original by row position/count (as done above) — there's no way to tell two
runs apart by looking at a single row in isolation. Worth adding a
`run_timestamp` column to every script's output before the next data
collection pass; would have made this comparison mechanical instead of
requiring `wc -l` and manual row-counting.

--- Follow-up: E3 re-run in isolation, same day ---
Re-ran `python3 experiments/scripts/exp3_cpu_stress.py --runs 20` on its own,
not preceded by E1/E2/E4 in the same session. Result: 20/20 detected.
  mean=2.64s stdev=0.57s min=1.51s max=4.02s  (n=20/20)

This resolves the ambiguity above in favour of hypothesis 3 (session/order
contention) over hypothesis 1 (a bug in exp3_cpu_stress.py or in the app's
self-monitoring thread) — the same script, same app, same machine, run in
isolation, worked cleanly all 20/20. Running E1, E2, and E4 immediately
beforehand (all in the same ~16-minute window as the original failing run)
is the more likely explanation than a defect in E3 itself.

One more honest observation, not yet explained: this isolated run's mean
(2.64s) is faster than both the original 20-run pass (5.65s) and the first
3 successful detections from the contaminated run (3.69s). Could be natural
run-to-run variance (the original data's own stdev was 3.68s, wide enough to
plausibly cover this), could be some other session-dependent effect (e.g.
Docker image/layer caching state, background host activity). Not
investigated further here — flagging rather than guessing.

Practical takeaway: experiments that share host resources are not fully
independent of each other when run back-to-back in one session on this
machine. If time allows, prefer running each experiment as its own isolated
invocation (or with a cooldown pause between them) rather than scripting all
five in immediate succession, and note in the paper's methodology that this
was observed and is why each experiment's run counts should be treated as
happening in a machine state that may carry over from whatever ran just
before it, unless explicitly isolated.

each experiment (run alone, not chained) reproduces the paper's numbers
cleanly across all five experiments.

--- What this means for the paper's numbers ---
The paper's numbers stand as originally reported — they come from the
original, first data-collection pass, which is what's summarized in
experiments/results/*_summary.csv already. This reproduction run is
additional, independently-collected evidence that the pipeline is
real and re-runnable, but it also surfaces genuine reliability questions
(specifically around E3, and to a lesser extent E2's docker_full case and
E4) that are worth investigating and are, if anything, a more honest
demonstration of real experimental work than a second clean run would have
been.
