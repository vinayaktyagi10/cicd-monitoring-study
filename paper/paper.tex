\begin{abstract}
We measured a small containerized pipeline (Docker, GitHub Actions, Prometheus and
Grafana) against uncontainerized and unmonitored baselines, then repeated the study on
the same hardware after reinstalling the operating system. Four measurement pitfalls
changed what the data appeared to show:
(P1)~\emph{zero pages are not memory pressure}: a zero-filled stress test stopped
triggering OOM kills on the replication kernel because its transparent-huge-page
shrinker reclaimed the zeroed pages;
(P2)~\emph{the load client measures the socket layer}: a client opening a new connection
per request measured ephemeral-port exhaustion in \texttt{docker-proxy}, not the
application;
(P3)~\emph{the sampling window outlasts the load}: \texttt{docker stats} samples longer
than a 0.11\,s load produced an apparent CPU-contention effect that kernel counters did
not confirm;
(P4)~\emph{absolute numbers do not travel}: most values moved by 12--173\% across the
reinstall, and by 27\% between two later sessions after routine package updates.
What held: the ordering of deployment times, the cost of re-running build and test on
every CI/CD deployment, recovery time after a container kill, and an OOM kill when memory
is resident. The first campaign's explanation of a throughput drop as CPU contention
between monitoring and application did not hold and is withdrawn: with a stable client
the monitoring stack used about 0.03 cores and cost at most about 1.4\% of throughput,
and the cost did not grow under background CPU load. For each pitfall we give the symptom, mechanism, evidence
and a check that prevents it. Raw data and a one-command rebuild of every table and
figure are published at \url{https://github.com/vinayaktyagi10/cicd-monitoring-study}.
\end{abstract}

\section{Introduction}

Evaluations of containerized deployment, CI/CD automation and monitoring stacks
usually report one measurement campaign on one host and treat the resulting numbers
as properties of the tools. We set out to do the same for a small pipeline: a
purpose-built FastAPI service, packaged with Docker, built and tested by a GitHub
Actions workflow, and monitored by Prometheus and Grafana. We measured deployment
time, resource use, throughput, and how quickly the monitoring detects induced CPU
saturation, memory exhaustion and container failure, against an uncontainerized
process and an unmonitored container. The first campaign told a clean story,
including a counter-intuitive one: adding monitoring containers lowered both the
application's CPU reading and its throughput, which we read as CPU contention
between the monitoring stack and the application.

\label{sec:intro-pitfalls}That story did not survive replication. Repeating the experiments on the same
hardware after the operating system was reinstalled moved most absolute numbers
outside their original confidence intervals, a memory-stress test that had
OOM-killed the container in every run stopped killing it at all, and the contention
effect disappeared. Tracing each change to a cause turned up four ways a container
or observability experiment can report something it did not measure:
\begin{enumerate}
\item[\textbf{P1.}] \textbf{Zero pages are not memory pressure.} On the replication
kernel, with transparent huge pages enabled, the kernel freed mostly-zero huge pages, so a
container holding zeroed memory reached its limit without being OOM-killed
(Section~\ref{sec:p1}).
\item[\textbf{P2.}] \textbf{The load client measures the socket layer.} A client that
opens a new TCP connection per request exhausts ephemeral ports within seconds, and
throughput then tracks \texttt{docker-proxy} system time, not the application
(Section~\ref{sec:p2}).
\item[\textbf{P3.}] \textbf{The sampling window outlasts the load.} A \texttt{docker
stats} reading that mostly misses a 0.11\,s burst makes CPU appear to fall as monitoring
is added (Section~\ref{sec:p3}).
\item[\textbf{P4.}] \textbf{Absolute numbers do not travel.} On the same hardware,
deployment times, throughput and detection latencies moved by 12--173\% after a reinstall
(Section~\ref{sec:p4}).
\end{enumerate}
None of these mechanisms is new on its own. What we add is evidence of how each one
produced a plausible, wrong or fragile result in a study that was otherwise
logged and repeated carefully, the diagnostic that exposed it, and a cheap check that
prevents it. The pipeline is the case study, not the contribution.

\subsection{Research Questions}
The case study asks four questions about the pipeline and one about the
measurements themselves.
\begin{itemize}
\item \textbf{RQ1.} How does containerization affect deployment time and resource
use, and what does CI/CD automation add?
\item \textbf{RQ2.} How quickly does Prometheus detect induced CPU saturation and
container failure?
\item \textbf{RQ3.} What does running Prometheus and Grafana alongside the
application cost?
\item \textbf{RQ4.} How reliable is the automated CI/CD deployment?
\item \textbf{RQ5.} Which of these findings survive a change of software
environment on the same hardware, and which measurement choices explain the ones
that do not?
\end{itemize}

\section{Contributions}
\label{sec:contributions}
\begin{enumerate}
\item \textbf{Four measurement pitfalls, each with mechanism and evidence.} For
P1 we show with a crossed diagnostic that disabling transparent huge pages for the
one process restores the OOM kill (Table~\ref{tab:thp}). For P2 we show throughput
collapsing as TIME\_WAIT sockets pass the ephemeral port range
(Fig.~\ref{fig:timewait}). For P3 we show the bimodal CPU reading and its
disappearance under kernel-counter measurement. For P4 we classify every finding
as reproducible or environment-dependent (Table~\ref{tab:reproducibility}).
Table~\ref{tab:pitfalls} gives the check that prevents each one.
\item \textbf{A retracted claim, reported as retracted.} The CPU-contention
explanation from the first campaign is tested against five of its own predictions and
withdrawn (Section~\ref{sec:contention}); what remains is a bound on monitoring
overhead of about 1.4\% of throughput.
\item \textbf{Case-study findings that held.} Deployment ordering, the CI/CD
build-and-test cost, recovery time after a container kill, peak CPU under stress, the
Prometheus and Grafana CPU draw, and the OOM kill with resident memory all
reproduced.
\item \textbf{A traceable artifact.} Raw per-run data, experiment and analysis
scripts, and a one-command rebuild of every table, statistic and figure from that
raw data (\texttt{make reproduce}, no Docker needed), with every number quoted in the
text checked against the data. Re-collecting data is repeatable but not
deterministic (Section~\ref{sec:limitations}).
\end{enumerate}

\section{Related Work}

This section covers the work closest to each tool in the case study and the two
methodology studies we position the pitfalls against. It is a targeted review, not a
systematic one. Table~\ref{tab:related} summarizes prior evaluations of the tools this
case study uses.

Felter et al.~\cite{felter2015} remains the most-cited apples-to-apples
comparison of native execution, Docker containers, and KVM virtual machines,
finding containers add near-zero CPU/memory overhead relative to native but
that both containers and VMs pay a cost on I/O-bound workloads. Lingayat et
al.~\cite{lingayat2018} and Mavridis and Karatza~\cite{mavridis2017} extend
this line to deployment/startup time and to containers nested inside VMs
respectively, but both stop at the container layer: neither introduces a
CI/CD pipeline or a monitoring stack, so their measurements cannot speak to
RQ2--RQ4. Ekanayaka et al.~\cite{ekanayaka2023} is the closest system to the
one built here --- \emph{KubFlow} integrates Git, Jenkins, ArgoCD, Terraform,
Docker, Kubernetes, Prometheus, and Grafana into a single DevOps
infrastructure --- but its evaluation is a pass/fail checklist of eight
qualitative test scenarios plus subjective colleague ratings, not a
quantitative, repeated-measures comparison against a non-monitored or
non-automated baseline.

Three further works bear directly on individual pillars. Dinga et
al.~\cite{dinga2023} empirically evaluate the energy and performance overhead
of four monitoring tools, Prometheus among them, on Docker-based systems and
report that the overhead depends on the tool and on the frequency and workload
conditions; this is the closest prior work on monitoring overhead, but it
isolates the monitoring tools and does not combine them with a CI/CD pipeline
or fault injection. Our Experiment~6, which measures the monitoring
containers' CPU from kernel counters, is complementary: it found
$\approx$0.03 cores for cAdvisor, Prometheus and Grafana together on this host,
which is compatible with a tool-dependent overhead but is a single
configuration and not a comparison across tools. Hilton et
al.~\cite{hilton2016} study the usage, costs and benefits of continuous
integration across 34{,}544 open-source GitHub projects, which motivates
measuring the cost of the CI step itself, as the Docker+CI/CD arm does.
Forsgren, Humble and Kim~\cite{forsgren2018} establish time-to-restore and
change-failure rate as standard software-delivery performance measures; our
MTTD and MTTR are the container-level analogues, measured in seconds on a
single service rather than as organization-level outcomes. Container
background is covered by Bernstein~\cite{bernstein2014}.

Two studies address measurement methodology rather than any one tool. Mytkowicz et
al.~\cite{mytkowicz2009} showed that setup details that look irrelevant, such as the size
of the UNIX environment and the link order, bias benchmark results enough to reverse a
conclusion, and that this bias goes unnoticed unless the setup is varied. Maricq et
al.~\cite{maricq2018} measured performance variability across many nominally identical
servers of a shared testbed and gave guidance on how many repetitions a claim needs and
on using nonparametric confidence intervals. Both concern general benchmarking: the
benchmark binary, the hardware and run-to-run variance.

\subsection{Positioning}
Each tool evaluation above reports a single measurement campaign, and none repeats its
measurements in a second software environment or reports a result that changed when
it was repeated. Dinga et al.~\cite{dinga2023} is the closest in subject and shows
that monitoring overhead depends on the tool and the workload; we do not compare
tools, and our overhead bound is for one configuration on one host. We make no claim
that combining containers, CI/CD and monitoring is itself a research question, nor
that the pitfalls in Section~\ref{sec:pitfalls} are individually unknown. Our
claim is narrower: in one replicated study, each of them produced a wrong or
fragile result that a single campaign would have reported as a finding, and each is
detectable with a cheap check. Relative to the methodology studies, P1--P3 are specific
to container and observability measurement: they come from the kernel's handling of a
container's memory, the container runtime's port proxy and the monitoring tool's sampling
window, not from the benchmark binary or the hardware. P4 is the lesson of Mytkowicz et
al.\ and Maricq et al.\ at a different level: on unchanged hardware, a change in the
software environment moved results further than a single campaign's intervals would
suggest. We follow Maricq et al.\ only in part: our main intervals are $t$-based, with
rank tests and bootstrap intervals as checks (Section~\ref{sec:stats}).

\textbf{Subject application.} Rather than an existing multi-service demo
application, the study uses a small, hand-built FastAPI service with three
endpoints designed as clean experimental levers: \texttt{/health} (a
near-constant-time route used as the load-test and liveness target),
\texttt{/cpu} (a configurable-iteration pure-Python busy loop used for CPU
stress), and \texttt{/memory} (a configurable-size heap allocation, optionally
retained, used for memory stress). This choice trades away the
multi-service realism of a demo application such as Sock Shop for the
ability to attribute every measured effect to a specific, known cause rather
than to inter-service scheduling or network confounds. The application
exposes Prometheus metrics natively via the
\texttt{prometheus\_client} library --- a request counter and latency
histogram per endpoint, plus two self-reported process gauges,
\texttt{app\_process\_cpu\_percent} and \texttt{app\_process\_memory\_bytes},
sampled every second from \texttt{time.process\_time()} and
\texttt{/proc/self/status} deltas respectively --- rather than through a
side-car exporter.

\subsection{Normal operation and baseline comparison (Experiment 1)}
Four configurations are compared, only two of which are baselines proper:
\emph{manual} (a raw \texttt{uvicorn} process, no container ---
\textbf{Baseline A}) and \emph{Docker} (a locally built and started
container, no CI/CD, no monitoring --- \textbf{Baseline B}). The remaining
two are not baselines but a progression toward the full stack: \emph{Docker+CI/CD} (a real GitHub Actions
\texttt{workflow\_dispatch} run --- test job then Docker build/push --- timed
end-to-end, then deployed) is an \textbf{intermediate configuration} that
isolates what automation alone costs, with monitoring still absent; and
\emph{full pipeline} (Docker Compose bringing up the application alongside
cAdvisor, Prometheus, and Grafana) is the \textbf{full stack}, adding
observability on top. This ordering --- Baseline A $\to$ Baseline B $\to$
Docker+CI/CD $\to$ full pipeline --- lets each of containerization,
automation, and observability be attributed its own marginal cost rather
than only the combined effect of all three at once. For each run, whatever
was previously running is torn
down, the configuration is started, and wall-clock time to the first
successful health check (and, for the full pipeline, to Prometheus and
Grafana also responding) is recorded.

\subsection{Resource utilization and monitoring overhead (Experiment 2)}
Three cases isolate the marginal cost of each monitoring layer: Docker only,
Docker+Prometheus(+cAdvisor), and Docker+Prometheus+Grafana(+cAdvisor). For
each of 20 runs per case, a fixed load (300 concurrent requests to
\texttt{/health}, concurrency 10) is issued while \texttt{docker stats} is
polled every second for every container in that case, giving per-container
mean CPU\% and memory alongside the load test's own throughput, mean/p95
latency, and error rate.

\subsection{CPU stress detection (Experiment 3)}
Eight threads concurrently flood \texttt{/cpu} (an 8-million-iteration
pure-Python loop per call) against the Docker+Prometheus case. Detection
time is measured as wall-clock time from load start until Prometheus first
reports the application's self-reported \texttt{app\_process\_cpu\_percent}
gauge at or above 60\%, polled every 0.5s.

\subsection{Memory stress / OOM behaviour (Experiment 4)}
The application container is run directly (not via Compose) with a hard
150\,MB memory limit and \texttt{--restart on-failure:1}. Repeated
\texttt{/memory?mb=20\&hold=true} calls accumulate retained allocations until
the kernel OOM-kills the container; \texttt{docker inspect} gives
ground-truth \texttt{OOMKilled} and \texttt{RestartCount}, captured at the
moment of observation since Docker resets \texttt{State.OOMKilled} once the
restart policy brings the container back up.

\subsection{Application failure and recovery (Experiment 5)}
Against the Docker+Prometheus case, the application container is killed
(\texttt{docker kill}) and Prometheus's \texttt{up\{job="app"\}} series is
polled every 0.3s until it reports 0 (detection time). The container is then
restarted (\texttt{docker start}) and both \texttt{/health} and
\texttt{up\{job="app"\}==1} are polled until both recover (recovery time).

\subsection{Monitoring overhead under controlled load (Experiment 6)}
\label{sec:e6method}
Added during validation because Experiment~2's $\approx$0.11\,s load window is
shorter than one \texttt{docker stats} sample. Four cases (Docker,
+cAdvisor, +Prometheus, +Grafana) each receive a closed-loop load of 20\,s
at concurrency 10 against \texttt{/health} on a freshly started stack, with
case order shuffled within each of 20 blocks. CPU is read from kernel
counters at exactly the start and end of the load window: \texttt{/proc/stat}
for the whole host, each container's cgroup v2 \texttt{cpu.stat}, the load
generator's own process time, and the \texttt{docker-proxy} processes that
forward the published port; whatever remains is unattributed background. A
CPU-pinned arm places the application, load generator and monitoring
containers on disjoint physical cores for the Docker and +Grafana cases. The
experiment was run twice with two load clients: the Experiment~2 client,
which opens a new TCP connection per request, and a keep-alive client that
reuses one HTTP/1.1 connection per worker
(\texttt{exp6\_overhead.py --keepalive}). Raw per-run rows (one per run, with
host, per-container and load-generator CPU, throughput and latency) are in
\texttt{experiments/raw/exp6\_overhead*.csv}
(four files: both clients, each at one and four load-generator processes); the

\section{Statistical Analysis}
\label{sec:stats}
Every interval and test below is computed from the per-run CSV rows, with
sample statistics (denominator $n{-}1$) and a two-sided $\alpha{=}0.05$, by
\texttt{stats\_lib.py} (unit-tested against \texttt{scipy}) and
\texttt{validate.py}. Table~\ref{tab:stats} lists each method with the reason
for choosing it and its main limit. We report intervals and effect sizes first
and $p$-values second: with 20 runs per cell a $p$-value alone says little
about whether a difference matters.
The Experiment~2 comparisons in Section~\ref{sec:results} quote Cohen's $d$
(\texttt{statistical\_analysis.py}); everywhere else we use Hedges' $g$, which
differs only by a small-sample correction (under 3\% at $n{=}20$ per group).

\textbf{Checking the assumptions.} We tested the 30 original-versus-replication
metrics of Table~\ref{tab:replication} (including the non-zero-fill Experiment~4 rows). A
Shapiro--Wilk test rejects normality in at least one of the two groups for 22 of 30 metrics,
so the $t$-based intervals are approximate for most of them. Welch's test and
Mann--Whitney agree on 27 of 30 metrics at $\alpha{=}0.05$, which
is why we report both. The disagreements are informative. MTTR has equal means
(0.7\% apart; Welch $p{=}0.52$) but a rank test separates the distributions
(Cliff's $\delta{=}-0.80$, Holm-adjusted $p{=}0.0002$): the replication's recovery times
are tighter, a difference in spread that is practically negligible for a metric
near 2.0\,s but is not ``identical''. Prometheus CPU under +Grafana and the
non-zero-fill time to OOM also split the two tests.

\textbf{Multiple comparisons.} The inline tests in the Results (the
Experiment~2 pairwise comparisons, the Experiment~6 contrasts, the four per-level
Experiment~7 penalties and the power-profile test in Section~\ref{sec:p4}) are not
corrected, and we say so where they appear. Experiment~7 had one test fixed before data
collection, the 60\% against 0\% difference-in-differences; its per-level intervals are
descriptive. For the replication comparison we
also computed Holm-adjusted $p$-values across all 30 metrics: 20 of 22 rows marked
different keep $p<0.05$ after the correction. The two that do not are the
non-zero-fill OOM rows. There the interval rule says different, while Welch's
test finds the two groups indistinguishable ($p{\approx}0.33$), because every
replication run is nearly identical (5 requests, 11.06\,s), so the rule's
interval collapses to a point. The interval rule and Welch's test agree on
28 of 30 metrics, and the two they split on are exactly these. We keep the
rule as stated, since it was fixed in advance, and read those two rows as
reproduced in Table~\ref{tab:reproducibility}.

\textbf{What we did not do.} We did not power the experiments for small effects:
the Experiment~6 keep-alive contrasts have 10--20 runs per case, so differences
near 1\% are at the edge of detection. We analyzed Experiment~6 as independent
groups although its runs come in randomized blocks, and a blocked or paired
analysis would likely be more sensitive. We did not model dependence between
sequential runs, which matters because throughput tracked host load in the
per-request client. We did not run a formal equivalence test, so ``consistent'' means
not distinguishable, not shown equal.

\subsection{CPU stress detection (RQ2)}
All 20 induced CPU-stress runs were detected by Prometheus, with mean time
to detect (MTTD) 5.65s (std 3.68s, min 1.51s, max 18.58s) and mean peak
self-reported CPU utilization 96.6\% (std 10.0, effectively pegged at one
full core, consistent with CPython's GIL limiting a single process to
$\approx$100\% of one core regardless of thread count). The detection floor
is set by the 2s Prometheus scrape interval combined with the 0.5s poll
granularity used to observe it; the long right tail (up to 18.58s) reflects
run-to-run variance in how quickly the OS scheduler favoured the eight
stress threads over the sampling thread, not a monitoring-pipeline delay.

An initial design used mean \texttt{/health} latency as the detection
signal instead of process CPU\%; it was rejected after finding it barely
moved under load, because CPython's GIL round-robins between threads at a
short, fixed interval ($\approx$5ms) regardless of how CPU-bound the
competing work is, so a trivial handler's queueing delay stays small even
under heavy contention.

\subsection{Memory stress and OOM behaviour (RQ2)}
All 20 runs triggered a genuine kernel OOM-kill and automatic restart
(\texttt{RestartCount}=1, confirmed via \texttt{docker inspect}), after a
mean 5.25 successful allocation requests (std 1.09) and a mean peak reported
memory of 135.54\,MB (std 0.17) against the 150\,MB hard limit. Mean
time-to-OOM was 11.58s (std 2.23s); this figure is dominated by the fixed
per-iteration overhead of the polling loop itself (a \texttt{curl}-equivalent
request, a \texttt{docker inspect} call, and a \texttt{docker stats} call
per iteration) rather than by the kernel's actual OOM response latency, and
should not be read as a monitoring detection time in the same sense as
Experiments 3, 5, and 6.

\subsection{Why the zero-filled allocation survives: kernel dependence (Experiment 4)}
\label{sec:oomkernel}
\textbf{Observation.} The unmodified Experiment~4 script held 20\,MB blocks of
zero-filled memory in a container limited to 150\,MB. Originally every run was
OOM-killed after about five requests. On the replication kernel none were: 0/20
runs were killed even after 16 requests ($\approx$320\,MB held against a
150\,MB limit), and the cgroup's \texttt{memory.events} showed the limit reached
without an OOM kill. Writing one non-zero byte per page
(\texttt{/memory?fill=true}) restored the original behaviour: 20/20 kills after a mean of
5.0 requests.

\textbf{Mechanism.} \texttt{bytearray(n)} writes its zeros, so the memory is resident
(an untouched mapping adds about 1\,MB; a 200\,MB \texttt{bytearray} adds 200\,MB even
with huge pages disabled). With transparent huge pages (THP) set to \texttt{always},
those writes are backed by 2\,MB pages. Recent kernels can split a huge page that is
mostly zero and free its zero subpages (the ``underused page'' shrinker, enabled here:
\texttt{shrink\_underused=1}). When the cgroup reaches its limit the kernel reclaims
memory that way instead of killing the process, so an allocation that is only zeros
never exhausts the limit. A non-zero byte in every 4\,KiB page makes each huge page
non-empty, so nothing can be freed and the OOM killer runs.

\textbf{Evidence.} A standalone probe (\texttt{diag\_thp.py}; same 150\,MB, no-swap
limit; up to 20 blocks of 20\,MB; 5 runs per cell) crosses the allocation pattern with
the THP policy, disabling THP for the probe process alone via \texttt{prctl}
(Table~\ref{tab:thp}). Only the zero-filled allocation under default THP survives, and
it is the only cell where the kernel's underused-huge-page split counter moves
(about 170 splits per run). Disabling THP for that one process, with the host, kernel,
container and limit unchanged, is enough to restore the OOM kill.

\textbf{What this means.} The OOM-kill result is conditional on the memory being
genuinely resident and non-reclaimable. We observed the zero-fill escape on one kernel
(7.2.9, THP \texttt{always}, \texttt{shrink\_underused=1}) on one machine; whether other
kernels or THP settings behave the same way we did not test. The safe practice does not
depend on that answer: a memory-stress test should write non-zero data, and a
fault-injection study that depends on memory pressure should report the kernel, THP
policy and fill pattern. The original finding stands for non-zero memory; for the
zero-filled variant it is a property of the kernel configuration.

\textbf{What is not established.} We did not record the original host's THP setting
and that installation no longer exists, so we cannot show that THP policy is what
differed between the original and replication runs. A distribution default of
\texttt{madvise}, under which a process that does not request huge pages behaves like
the ``disabled'' rows, would be consistent with the original result, but we did not test
it. We showed that process-level THP is sufficient to flip the outcome here; we did not
toggle the host-wide \texttt{shrink\_underused} setting (it needs root), and we did
not test other kernel versions.

\subsection{Monitoring overhead under controlled load (Experiment 6)}
\label{sec:e6results}
Experiment~6 gave two different answers depending on the load client, and
the difference is itself a finding. With the Experiment~2 client, which opens a
new TCP connection per request, throughput ranged from 92--2{,}492\,req/s and
25 of 120 runs below 500\,req/s, with within-case variation of at least
40\%. Throughput tracked host load ($r{=}-0.98$ with host busy cores) and,
more tightly, the CPU time of the docker-proxy processes that forward
the published port ($r{=}-0.991$, 95\% CI $[-0.994, -0.986]$);
docker-proxy used 4.8--9.6 cores in these runs. A separate
diagnostic (3 repetitions per client, 40\,s each) explains why. The
host has 28{,}232 ephemeral ports; the per-request client reached
42{,}205 TIME\_WAIT sockets, throughput fell from 3{,}501\,req/s in the
first 5\,s to 120\,req/s after 30\,s, and docker-proxy spent 9.1 cores
of system time against 0.04 of user time (Fig.~\ref{fig:timewait}). With
keep-alive connections the same host sustained 6{,}350\,req/s throughout with
at most 20 TIME\_WAIT sockets and docker-proxy at 0.11 cores.
The per-request client therefore mostly measures socket exhaustion on the
host over a 20\,s load, not the application or the monitoring stack, so its
Experiment~6 throughput cannot be attributed to monitoring. Experiment~2's
300-request burst is too short to exhaust the ports, so this does not explain
its throughput trend; that trend did not reproduce in the replication
(Section~\ref{sec:replication}), and the keep-alive result below bounds the
effect at about 1.4\%.

The keep-alive client is stable (within-case variation at most 2.3\%) and

neither supports nor excludes a contention effect of that size. One
configuration does detect a difference: against Docker alone, +Grafana with
four load-generator processes ($-1.4$\%, 95\% CI $[-159, -36]$\,req/s) is lower, and
the interval excludes zero (10 runs per case). We did
not correct for the number of contrasts examined, and the 20-run
and 10-run designs were not powered for effects this small. We therefore
report a bound, not an absence: on this host, with a client that does not
exhaust ports, monitoring costs at most about 1.4\% of throughput, and one
of the two keep-alive configurations detects a loss of that size. We did not
identify its mechanism.

\subsection{Monitoring cost under background CPU load (Experiment 7)}
\label{sec:e7results}
Contention predicts that the monitoring cost grows as the host gets busier. Experiment~7
repeated the keep-alive measurement for Docker alone and the full stack while a duty-cycle
burner on all 16 logical CPUs held a background target of 0, 20, 40 or 60\% (cells shuffled
within blocks, 15 runs per cell, burner CPU read from \texttt{/proc}; achieved 2.4 busy cores,
5.5 busy cores, 8.6 busy cores and 12.0 busy cores). The monitoring containers used
0.038--0.053 cores, and the penalty (Docker-only minus full-stack throughput) did not grow
(Fig.~\ref{fig:loaded}): $-4$\,req/s, 95\% CI $[-219, +210]$ ($-0.1$\%) at 0\%;
$+113$\,req/s, 95\% CI $[-29, +255]$ ($+2.6$\%) at 20\%; $+24$\,req/s, 95\% CI $[-89, +138]$
($+0.6$\%) at 40\%; $-13$\,req/s, 95\% CI $[-399, +373]$ ($-0.4$\%) at 60\%. The test fixed
before data collection, a difference-in-differences $-9$\,req/s, 95\% CI $[-424, +389]$
between 60\% and 0\%, leaves contention not supported. With run-to-run variation of
3--6\%, rising to up to 16\% at the 60\% level, the experiment only rules out a load-dependent
penalty above about 11\% of throughput, so it confirms that there is no large contention effect
and adds nothing finer than Experiment~6.

\subsection{Revised explanation of the CPU-contention finding}
\label{sec:contention}
\textbf{Original claim.} In the original run the application's CPU reading fell
(11.0\% $\to$ 3.8\% $\to$ 1.8\%) and throughput fell (2737 $\to$ 2641 $\to$
2449 req/s, $-10.5\%$) as monitoring containers were added. We explained both
by host-level CPU contention: the monitoring stack competes with the application
for cores, so the application is scheduled less. We no longer hold this as a
supported conclusion.

\textbf{What contention predicts, and what Experiment~6 found.}
\begin{enumerate}
\item \emph{The monitoring containers should use meaningful CPU.} They did not:
about 0.03 cores in total, measured from kernel counters.
\item \emph{Throughput should fall when monitoring is added, with a stable
client.} It fell by at most 0.9\% with one load-generator process and by 1.4\%
with four, against the 10.5\% originally read.
\item \emph{Moving the monitoring containers to cores the application does not
use should remove the drop.} The pinning test is inconclusive in both clients:
a difference-in-differences of $+376$\,req/s, 95\% CI $[-343, +1061]$ with the
per-request client and $+8$\,req/s, 95\% CI $[-94, +105]$ with the keep-alive
client. It neither supports contention nor excludes an effect of that size.
\item \emph{Runs with more monitoring CPU should have lower throughput.} With
the stable client they do not: across all runs $r{=}-0.13$, 95\% CI $[-0.34, +0.09]$,
and within a case $r{=}-0.07$, 95\% CI $[-0.28, +0.16]$. With four load-generator
processes the pooled association is $r{=}-0.63$, 95\% CI $[-0.84, -0.25]$, but within
a case it is $r{=}-0.16$, 95\% CI $[-0.58, +0.31]$: it comes from the Docker-only
against monitored contrast, not from the amount of monitoring CPU.
\item \emph{The monitoring penalty should grow as the host gets busier.} It did not
(Experiment~7, Section~\ref{sec:e7results}): no level from 0 to 60\% background load
shows a penalty whose interval excludes zero, and there is no trend across levels.
\end{enumerate}

\textbf{Revised explanation.}
(i)~The fall in application CPU\% is a measurement artifact of a 0.11\,s load window
sampled by a longer interval (Section~\ref{sec:results}), not a scheduling effect.
(ii)~The original throughput drop cannot be attributed to monitoring. It did not
reproduce (replication means of 4041, 3996 and 4033\,req/s have no ordering), and with
a client that does not exhaust ports the monitoring effect is at most 1.4\%, several
times smaller. What did drive throughput in the per-request client was socket exhaustion
and host load (Section~\ref{sec:e6results}). (iii)~What remains is a loss of about 1.4\% in
one of two keep-alive configurations, associated with about 0.03 cores of monitoring CPU.
We did not identify its mechanism; contention is one candidate that we have not tested
and that the evidence above does not favour over run-to-run variation; Experiment~7
found no growth with load, though it can detect only large growth.

\textbf{Status.} Retracted as a supported conclusion. Experiments~6 and~7 exclude
large contention effects on this host, including a large load-dependent one; they do
not exclude effects of about 1\% or smaller, and neither the pinning test nor the
load test is precise enough to say whether any such effect is contention.

installed operating system (CachyOS, kernel 7.2.9, Docker 29.8.2) in place of

robustness to the software environment rather than to run-to-run noise alone.
Results were written to a separate directory so
the data behind Tables~\ref{tab:deploy}, \ref{tab:resource}

\section{Four Measurement Pitfalls}
\label{sec:pitfalls}
Each pitfall below turned a property of the measurement apparatus into an apparent
property of the system under test, and none was visible in the summary statistics of a
single campaign. P1 and P4 surfaced only because the study was repeated in a second
software environment; P2 and P3 only because the same quantity was re-measured with a
different instrument. Table~\ref{tab:pitfalls} summarizes them.

\subsection{P1: Zero pages are not memory pressure}
\label{sec:p1}
\emph{Symptom.} The memory-stress test that OOM-killed the container in 20/20 original
runs killed it in 0/20 replication runs, although 16 requests ($\approx$320\,MB) succeeded
against a 150\,MB limit. \emph{Mechanism.} The allocation is zero-filled. On the replication
kernel, with transparent huge pages enabled and the underused-huge-page shrinker active, the
kernel splits mostly-zero huge pages and frees their zero subpages under cgroup pressure,
so the limit is reached without an OOM kill. \emph{Evidence.} Disabling THP for the one
probe process restores the kill, and only the surviving cell moves the split counter
(Table~\ref{tab:thp}, Section~\ref{sec:oomkernel}). \emph{Fix.} Write non-zero data to
every page, check \texttt{memory.events} for \texttt{oom\_kill}, and report the kernel, THP
policy and fill pattern.

\subsection{P2: The load client measures the socket layer}
\label{sec:p2}
\emph{Symptom.} With a client that opens a new TCP connection per request, throughput
varied three-fold between runs and tracked the CPU time of \texttt{docker-proxy}.
\emph{Mechanism.} The client exhausts the host's ephemeral ports within seconds; TIME\_WAIT
sockets pile up and \texttt{docker-proxy} spends its time in the kernel, so throughput
measures the host's socket layer, not the application. \emph{Evidence.} Per-second
TIME\_WAIT and proxy CPU series show the collapse, and a keep-alive client on the same host
is flat (Fig.~\ref{fig:timewait}, Section~\ref{sec:e6results}). \emph{Fix.} Use keep-alive
connections, record TIME\_WAIT and client and proxy CPU, and check within-case variation
before comparing cases.

\subsection{P3: The sampling window outlasts the load}
\label{sec:p3}
\emph{Symptom.} The application's CPU reading fell as monitoring containers were added,
which we first reported as CPU contention. \emph{Mechanism.} The Experiment~2 load lasts
about 0.11\,s and a \texttt{docker stats} reading covers a longer interval, so many runs
read idle and the mean counts how often the sample missed the burst. \emph{Evidence.} The
per-run readings are bimodal, and kernel counters read over the exact load window show the
monitoring containers using about 0.03 cores with no contention effect
(Sections~\ref{sec:results} and~\ref{sec:contention}). \emph{Fix.} Use a fixed-duration
load and read cgroup \texttt{cpu.stat} at the edges of the load window.

\subsection{P4: Absolute numbers do not travel}
\label{sec:p4}
\emph{Symptom.} After the operating-system reinstall, deployment times, throughput and
detection latencies moved by 12--173\% on the same hardware (Section~\ref{sec:replication}).
Later, the same keep-alive Docker-only measurement gave 6{,}559\,req/s in Experiment~6 and
4{,}759\,req/s in Experiment~7, a week apart ($-27$\%), with unattributed background CPU
of 0.63 cores against 0.32 cores in Experiment~6. \emph{Mechanism, partly tested.} The
campaign snapshots show that Experiment~7 ran on battery with the balanced power profile,
while Experiment~6 ran on AC with the performance profile. We tested that directly on AC,
alternating profiles in four blocks: medians of 5{,}035\,req/s under performance and
4{,}889\,req/s under balanced, 12 runs per profile. Across all runs the difference is
$-278$\,req/s, 95\% CI $[-945, +390]$, because 2 runs at half speed fell in a performance
block; without them (a post-hoc exclusion) it is $+171$\,req/s, 95\% CI $[114, 228]$
($+3.5$\%). The power profile therefore explains a few percent, not the gap. Between the two
experiments Docker was updated from 29.8.2 to 29.9.0 and the kernel package was rebuilt
(7.2.9-1 to 7.2.9-2) by routine system updates; \texttt{docker-proxy} carries every request,
so these are the remaining candidates, but we did not test them. \emph{Fix.} Record the full
software environment, including package versions and power state, with every run; pin
versions for the duration of a study; and compare configurations only within one session.

\section{Discussion}

\subsection{Answers to the case-study questions}

\textbf{RQ1 (containerization's effect on deployment time and resource
use).} Containerization has a small, consistent fixed cost at deployment
time ($\approx$0.86s here) and a resource footprint dominated by the
application's own working set (36\,MB) rather than by container overhead
per se --- consistent with the classic finding in
Felter et al.~\cite{felter2015} that containers add near-zero CPU/memory
overhead relative to native execution. The more consequential RQ1 finding in
this study is that a CI/CD-automated deployment is not simply "Docker plus a
trigger": it is roughly 35$\times$ slower end-to-end because it re-runs the
full build-and-test cycle, a cost invisible to studies (such as
Lingayat et al.~\cite{lingayat2018}) that measure only container startup
time in isolation.

\textbf{RQ2 (monitoring's effect on detecting degradation and failure).}
Prometheus detected every induced CPU saturation event and every container
failure, 20/20 in each experiment in both the original run and the replication. That
detection succeeds is the finding that holds. How fast it succeeds did not: the original
run detected failures (mean 1.15s) about five times faster than CPU saturation (mean
5.65s), but the replication inverted the ordering (3.14s against 2.41s), so both
detection times are environment-sensitive (Table~\ref{tab:reproducibility}) and we draw
no conclusion about which kind of event is detected faster. Unlike the pass/fail
scenarios of Ekanayaka et al.~\cite{ekanayaka2023}, these are repeated timed
measurements, but on one host they bound only this configuration.

\textbf{RQ3 (monitoring overhead).} The original run suggested a structurally
unusual overhead: monitoring containers competing with the application for
cores, cutting throughput by 10.5\% while the application's own CPU\% fell. Experiment~6
retracts that explanation (Section~\ref{sec:contention}). The CPU\% fall was a
measurement artifact; the monitoring containers drew about 0.03 cores; and with a
stable client throughput was within 1.4\% of Docker-only, a loss one of two
configurations detects and whose mechanism is unidentified. Under background CPU load up
to 60\% the penalty did not grow (Experiment~7). Our answer to RQ3 is therefore a
bound: on this host the Prometheus--Grafana stack costs at most about 1.4\% of
throughput and about 0.03 cores, and cAdvisor dominates the tooling's own CPU draw in
the original run but not in the replication (6.1\% against 2.4\%).

\textbf{RQ4 (does automated CI/CD plus monitoring improve reliability).}
The evidence here is mixed and should be stated honestly: CI/CD automation
was reliable (7/8, 87.5\%) but not perfect, and the one observed failure was
attributable to a transient delay in the trigger step rather than to the
pipeline's own robustness. Critically, 87.5\% is a point estimate that
should not be quoted on its own: the 95\% Wilson score interval for 7
successes out of 8 trials is $[52.9\%, 97.8\%]$ --- at this sample size the
data are consistent with anywhere from roughly half to nearly all CI/CD
deployments succeeding, and the point estimate alone overstates the
precision of the claim. A larger $n$ for the CI/CD arm (constrained here
by real GitHub Actions minutes and wall-clock cost, Section~\ref{sec:limitations})
would be needed to narrow this interval and bound the reliability claim more
tightly.

\textbf{RQ5 (what survives a change of environment).}
Table~\ref{tab:reproducibility} gives the full classification. Relative and
structural findings held: the deployment ordering, the CI/CD build-and-test cost,
recovery time, peak CPU under stress, the Prometheus and Grafana CPU draw, and the
OOM kill when memory is resident. Absolute timings, throughput, latency and detection
times did not, and two explanations offered in the first campaign (CPU contention as
the cause of the throughput drop and of the falling CPU reading) are not supported.
Every finding that failed to reproduce traces to one of the pitfalls in
Table~\ref{tab:pitfalls} or to the environment change itself.

\section{Limitations}
\label{sec:limitations}

\begin{itemize}
\item \textbf{Replication on the same hardware did not reproduce most
absolute numbers.} Re-running Experiments 1--5 with the unmodified scripts on
the same machine after the operating system was reinstalled (CachyOS, kernel
7.2.9, Docker 29.8.2, replacing Arch/Omarchy 7.1.9; performance power profile;
20 runs each)
(Table~\ref{tab:replication}) gave deployment times 12--29\% faster, throughput about 48\% higher, CPU-stress
detection of 2.41s rather than 5.65s and failure detection of 3.14s rather
than 1.15s, with the mean outside the original 95\% interval for most metrics.
Only the Docker+CI/CD deployment time (48.6\,s vs.\ 50.2\,s; 8/8 real
GitHub Actions runs succeeded vs.\ 7/8 originally), MTTR, peak CPU under
stress, the Prometheus/Grafana CPU figures and the application CPU\% in the
+Prometheus and +Grafana cases stayed consistent; the replication success rate
has a 95\% Wilson interval of [0.68, 1.00], so it does not contradict the
original 7/8. The
deployment ordering (manual, then Docker, then full pipeline) was preserved,
but the throughput ordering across monitoring cases was not (4041, 3996 and
4033\,req/s for Docker, +Prometheus and +Grafana); absolute values are
specific to one software environment.
\item \textbf{The CPU-contention explanation is not supported.} Experiment~2's
application CPU\% is bimodal because its $\approx$0.11s load window is sampled
by a longer \texttt{docker stats} interval, so the reported fall with
monitoring is mostly runs that read as idle. A new Experiment~6 (20 runs per
case, fixed 20s load, CPU from kernel counters over exactly the load window,
randomized case order, optional CPU-pinned arm) found the monitoring
containers used $\approx$0.03 cores in total, and the per-request client showed
no throughput difference from Docker-only whose 95\% interval excluded zero. That
client is unreliable: its throughput varied roughly three-fold, tracked host load
($r{=}-0.98$ with host busy cores) and collapsed as TIME\_WAIT sockets exhausted
the ephemeral ports (Section~\ref{sec:e6results}), so its pinning result
(difference-in-differences $+376$\,req/s, 95\% CI $[-343, +1061]$) is
inconclusive. A keep-alive client is stable and bounds the monitoring cost at
about 1.4\% of throughput, but one of its two configurations (four load-generator
processes, 10 runs per case, no multiple-comparison correction) detects a loss of
that size whose mechanism we did not identify. The experiments can rule out large
monitoring overhead on this host; they cannot rule out small effects.
\item \textbf{What is and is not reproducible.} From the committed raw data,
\texttt{make reproduce} rebuilds every table, statistic and figure in the paper
without Docker: unit tests, summary tables checked against the committed copies,
every number quoted for Experiments 1--5 and 6 found verbatim in the paper,
confidence intervals and effect sizes, and every plotted figure compared pixel
for pixel. Two things are outside that guarantee. First, re-running the
experiments (\texttt{make campaign}) collects new measurements, and the
replication shows these differ with the software environment, so a rerun
reproduces the procedure, not the numbers. Second, Fig.~\ref{fig:grafana} is a
screenshot of a live dashboard and differs on every capture; only the underlying
Prometheus series are saved. The original 2026-09 host (kernel, THP setting) no
longer exists, so the original runs themselves cannot be re-executed under their
original conditions.
\item \textbf{Experiment 4 depends on kernel behaviour} (mechanism and
evidence in Section~\ref{sec:oomkernel}). The retained
allocation is zero-filled. On the replication kernel, which enables transparent
hugepage shrinking of zero-filled pages (\texttt{shrink\_underused=1}), the
kernel reclaimed that memory under cgroup pressure, so 0/20 containers were
OOM-killed even though 16 requests ($\approx$320\,MB) succeeded against a
150\,MB limit. With the allocation writing a non-zero byte to every page
(\texttt{/memory?fill=true}, default off), 20/20 runs were OOM-killed after a
mean 5.0 requests with peak memory 136.4\,MB, close to the original
result (5.25 requests, 135.5\,MB; the interval rule of Table~\ref{tab:replication}
marks these rows different because the replication runs are nearly identical). The OOM finding therefore holds when the
memory is genuinely resident; the original zero-filled variant is kernel
dependent. The original run was on a different distribution and kernel
(Arch 7.1.9 vs.\ CachyOS 7.2.9); the replication host has transparent
hugepages set to \texttt{always}. We did not record the original host's THP
setting and the original installation no longer exists, so we cannot confirm
that this setting is what differed; the distribution default being
\texttt{madvise} is a plausible but untested explanation.
\item \textbf{cAdvisor produced no usable per-container series.} This host's Docker
stores images through the containerd snapshotter (\texttt{docker info}: storage driver
\texttt{overlayfs}, \texttt{io.containerd.snapshotter.v1}), not the classic
\texttt{overlay2} layout. cAdvisor v0.49.1 logged that it could not identify the
read-write layer of any container and attached no container name or image label, so
Prometheus queries filtered by container returned nothing. Three consequences follow.
The detection experiments use the application's own Prometheus metrics, so their
detection times are for an application-level signal, not for container-level CPU. The
per-container CPU and memory figures come from \texttt{docker stats} and cgroup
counters, not from the monitoring stack. cAdvisor still ran and was scraped in every
monitored case, so its CPU is included in the overhead figures, but we did not measure
the cost of a cAdvisor that resolves labels. We tested one cAdvisor version with one
storage driver; this is not a statement about cAdvisor in general, and other versions
or the \texttt{overlay2} driver may behave differently.
\item \textbf{GHCR authentication.} The Docker+CI/CD deployment step could
not pull from GitHub Container Registry (the CLI token used lacks the
\texttt{read:packages} scope, which would require an interactive browser
re-authentication out of scope for an unattended experiment run) and instead
deploys the locally built image from the same commit and Dockerfile CI just
built. The CI timing itself (test + build + push) is unaffected and fully
real.
\item \textbf{Reduced $n$ for the CI/CD arm.} Only 8 (vs.\ 20 for the other
three deployment configurations) real GitHub Actions runs were triggered,
because each run costs $\approx$45--65s of real CI wall time and consumes
Actions minutes; this narrows the confidence interval on the CI/CD reliability
and timing figures relative to the other three configurations.
\item \textbf{Single-host measurement.} All experiments ran on one physical
machine with no isolation from other host activity beyond what Docker itself
provides; absolute timing figures (especially the sub-2s deployment times)
should be read as relative comparisons between configurations on this host,
not as portable absolute benchmarks.
\item \textbf{Experiment~7 precision and conditions.} Its 15 runs per cell bound only
a large load-dependent penalty. It ran on battery with the balanced power profile
(Section~\ref{sec:p4}); that state was constant within the experiment, so its
within-experiment contrasts stand, but its throughput levels are not comparable with
Experiment~6. The 60\% target loads 16 logical CPUs on 8 physical
cores, so it is not saturation, and SMT sharing adds noise at that level. Its
background-CPU precondition was relaxed from 0.5 to 1.5 cores because the
interactive desktop could not be closed; unattributed CPU is recorded per run.
\item \textbf{Detection thresholds are fixed, not tuned.} The 60\%
CPU-percent threshold (Experiment 3) and the memory container limit (150\,MB,
Experiment 4) were chosen to make the induced condition reliably observable
within a short polling window rather than to model a specific production SLO;
detection-time figures should be read relative to these thresholds, not as
threshold-independent constants.
\item \textbf{Not every reported difference is statistically significant.}
Welch's $t$-tests on the raw per-run data (\texttt{statistical\_analysis.py})
confirm the Docker-to-+Grafana endpoints of the throughput and CPU\% trends
in Section~\ref{sec:results} ($p{<}0.01$ for both), but two things reported
only as directional observations do not reach significance at
$\alpha{=}0.05$: the latency increase across all three monitoring cases
($p \geq 0.36$ for every pair), and the middle step of the throughput trend
(Docker vs.\ +Prometheus, $p{=}0.177$). Means and standard deviations alone,
without this check, would have overstated how uniformly these effects hold
run-to-run.
\end{itemize}

\section{Conclusion}

A small, carefully logged study of a containerized CI/CD pipeline with
Prometheus--Grafana monitoring produced a clean set of findings on its first run.
Repeating it on the same hardware after an operating-system reinstall showed which of
them were properties of the pipeline and which were properties of how we measured it.
What held: the ordering of deployment times, the cost of re-running build and test on
every CI/CD deployment, recovery time after a container kill, and an OOM kill when
memory is resident. Monitoring cost at most about 1.4\% of throughput and about 0.03
cores with a stable client, and the first campaign's CPU-contention explanation is
withdrawn. Whether a loss of about 1\% exists, whether CPU pinning changes it, and what
caused a 27\% drift between two later sessions remain inconclusive. What did not hold
traced to four pitfalls: kernel reclaim
of zero-filled memory, a load client that measured socket exhaustion, a sampling
window longer than the load, and absolute numbers that do not travel across software
environments. Each has a cheap check (Table~\ref{tab:pitfalls}). The raw data,
scripts and a one-command rebuild of every table and figure are published at
\url{https://github.com/vinayaktyagi10/cicd-monitoring-study}.
